# v0.1.0 — Initial MVP

- **Status:** Active
- **Target version:** v0.1.0
- **Created:** 2026-07-31
- **Last updated:** 2026-07-31
- **Project timezone:** Asia/Shanghai
- **Primary branch sequence:** short-lived `feature/v0.1-*` branches, followed by `release/v0.1` only if stabilization requires it
- **Current repository state:** Git is initialized on `main` with the GitHub origin configured; application code has not been initialized

## 1. Objective

Deliver the first complete, secure, and maintainable version of Zotero arXiv Daily.

Version v0.1.0 must build a compact interest profile from the user's complete local Zotero library, including notes and PDF annotations; discover recent and adjacent-category arXiv papers; produce approximately 20 explainable recommendations through local pre-ranking and `deepseek-v4-flash`; publish encrypted or explicitly public static results to GitHub Pages; and collect feedback that can influence later runs.

The MVP is a complete vertical workflow, not a collection of disconnected prototypes.

## 2. Release Acceptance Criteria

Version v0.1.0 is complete only when all criteria below are met:

- A clean local installation can run `doctor`, connect to Zotero Local API, and explain configuration failures without exposing secrets.
- The complete Zotero library can be synchronized once and then incrementally by library version.
- Metadata, collections, manual tags, notes, PDF highlights, and annotation comments are represented as distinct interest signals.
- Raw notes, annotations, PDF text, and complete Zotero records never enter Git, GitHub Actions inputs, logs, fixtures, or Pages output.
- A compact, versioned interest profile can be generated deterministically from unchanged local inputs without repeated LLM work.
- The protected remote profile is allowlisted, size-bounded, and publishable to GitHub Actions without command-line secret exposure.
- arXiv retrieval uses the official API, one connection at a time, with at least three seconds between requests.
- Retrieval resumes from the last successful checkpoint with an overlap window and deduplicates paper revisions by canonical arXiv ID.
- Candidate retrieval can expand from core categories to one-hop adjacent categories under explicit quotas.
- Local pre-ranking reduces the candidate set before any LLM ranking request.
- DeepSeek responses are structured, validated, bounded by a token/request budget, and unable to control persistence, URLs, or executable actions.
- The final result targets 20 papers using core, adjacent, and exploration quotas while allowing fewer papers below the quality threshold.
- Every recommendation has a validated title, authors, category, date, abstract/PDF links, Chinese summary by default, and an explainable recommendation reason.
- The static site supports today's recommendations, historical dates, filtering, responsive layout, and feedback controls.
- Production recommendation data is encrypted for client-side decryption by default; an explicit public-output mode is available.
- Feedback is stored locally in the browser and can be synchronized as one batched, prefilled GitHub Issue without exposing a token in the browser.
- Scheduled and manual GitHub Actions workflows are idempotent, concurrency-safe, and preserve the previous usable site on failure.
- The repository passes formatting, lint, type, unit, contract, integration, end-to-end, static-build, secret, and private-data checks.
- Installation, local profile synchronization, GitHub configuration, daily operation, recovery, and release procedures are documented in English.
- A release candidate passes a cost-bounded live smoke test before the immutable `v0.1.0` tag is created.

## 3. Scope

### 3.1 Included

- Python project, CLI, configuration, schemas, logging, storage, and test foundation.
- Local Zotero API access and diagnostics.
- Full and incremental Zotero synchronization.
- Notes and PDF annotation parsing and signal extraction.
- Per-item digests and hierarchical interest profile construction.
- Protected profile export and GitHub Actions secret publication.
- arXiv category inference, adjacent-category mapping, retrieval, normalization, throttling, caching, and checkpoints.
- Local text-based pre-ranking without a vector database.
- DeepSeek provider adapter, structured prompts, ranking, summarization, and explanation.
- Deduplication, quality thresholds, quotas, and diversity selection.
- Versioned recommendation and run-manifest schemas.
- Static site generation, history, filters, links, and client-side feedback.
- Authenticated client-side encryption for production recommendation data.
- Batched GitHub Issue feedback and idempotent feedback ingestion.
- Scheduled/manual GitHub Actions and GitHub Pages deployment.
- CI, documentation, security checks, recovery procedures, and release packaging.

### 3.2 Explicit Non-goals

- Multi-user accounts or a hosted SaaS backend.
- Automatic Zotero write-back.
- Email, WeChat, Slack, or mobile push notifications.
- Hosting or redistributing arXiv PDFs.
- Daily processing of complete PDF full text.
- A vector database or remote embedding service.
- A SPA framework or server-rendered web backend.
- Real-time recommendations or conversational search.
- Learned ranking trained on a large feedback corpus.
- Cross-device automatic feedback synchronization without the explicit GitHub Issue step.
- Guaranteed private GitHub Pages access control; v0.1.0 protects content with client-side encryption instead.

## 4. Architectural Baseline

### 4.1 Local Profile Flow

```text
Zotero Local API
  -> normalized bibliographic items
  -> normalized notes and annotation signals
  -> local SQLite cache and content hashes
  -> per-item ItemDigest records
  -> hierarchical InterestProfile
  -> redacted, size-bounded RemoteProfile
  -> protected GitHub Actions secret/input
```

The local profile flow owns raw Zotero content. No remote stage may request the original local database, raw note HTML, full annotations, or PDF text.

The first release uses deterministic local normalization and extractive signal processing before any model call. If DeepSeek is used during profile aggregation, it receives only allowlisted, capped `ItemDigest` data rather than raw Zotero content.

### 4.2 Daily Remote Flow

```text
RemoteProfile + processed feedback + last successful checkpoint
  -> derive core and adjacent arXiv categories
  -> retrieve bounded recent candidates
  -> normalize and deduplicate
  -> remove already known or recently recommended papers
  -> local pre-ranking
  -> DeepSeek structured ranking and summaries
  -> quality, quota, and diversity selection
  -> validated RecommendationSet and RunManifest
  -> authenticated encryption
  -> static site build and GitHub Pages deployment
  -> atomically advance checkpoint and feedback state
```

### 4.3 Feedback Flow

```text
Recommendation cards
  -> browser localStorage
  -> one batched prefilled GitHub Issue
  -> GitHub Actions feedback ingestion
  -> idempotent normalized Feedback records
  -> next-run penalties, boosts, and profile-review signals
```

The browser never contains a GitHub token. Issue submission requires an explicit user confirmation. Long-term negative preferences require repeated explicit feedback and are not inferred from a single click.

### 4.4 State Ownership

| State | Owner | Storage baseline |
| --- | --- | --- |
| Raw Zotero content | Local profile tool | Local SQLite and transient memory only |
| Item content hashes and digests | Local profile tool | Local SQLite |
| Remote interest profile | User/GitHub Actions | GitHub Actions Secret or equivalent protected input |
| DeepSeek key | User/GitHub Actions | Local credential store and GitHub Actions Secret |
| arXiv checkpoint | Daily pipeline | Dedicated state branch or equivalent protected state store |
| Processed feedback IDs | Daily pipeline | Dedicated state branch or equivalent protected state store |
| Recommendation history | Static publisher | Authenticated encrypted files in state/publish output |
| Run manifests | Daily pipeline | Non-sensitive state records |
| Browser pending feedback | Static client | Versioned `localStorage` record |

State persistence must be atomic. A failed run must not advance the arXiv checkpoint, consume feedback, or replace the previous usable recommendation site.

## 8. Milestone Details

### V01-M0 — Engineering Foundation

**Goal:** Establish a minimal, reproducible, testable project without pre-building unused architecture.

**Implementation:**

- Initialize Git and create the protected-main workflow when GitHub is available.
- Create `pyproject.toml`, the package, `uv.lock`, `.gitignore`, license decision, and README skeleton.
- Add configuration loading with environment/file/CLI precedence and strict startup validation.
- Add the authoritative application version source and initial schema-version constants.
- Add the error taxonomy, structured logging, clock abstraction, run IDs, and exit-code policy.
- Add initial domain models for IDs, timestamps, profile envelopes, recommendations, feedback, and run manifests only as required by near-term work.
- Add the CLI root and `doctor` command.
- Add formatting, lint, static typing, pytest, sanitized fixtures, CI, secret scanning, and artifact inspection.
- Introduce ADR storage and record decisions for protected profile transport, remote state ownership, and Pages encryption if validation changes the baseline.

**Exit criteria:**

- A clean checkout installs from the lock file.
- `doctor` reports missing Zotero, DeepSeek, GitHub, and Pages configuration independently.
- CI runs offline without production secrets.
- No empty feature directories or placeholder services are added.
- README documents conceptual setup without claiming unimplemented commands work.

### V01-M1 — Local Zotero Synchronization

**Goal:** Build a reliable local representation of the complete Zotero library and its interest signals.

**Implementation:**

- Detect Zotero Local API version and enabled/disabled state.
- Fetch user library items, collections, child relationships, notes, and annotations through documented API endpoints.
- Normalize bibliographic fields, creators, tags, collections, identifiers, dates, and parent-child relationships.
- Preserve manual versus automatic tags.
- Distinguish normal notes, highlighted source text, and user annotation comments.
- Sanitize note HTML and normalize Unicode and whitespace.
- Exclude trashed items and prevent attachments from becoming independent recommendation seeds.
- Store normalized local state, library version, item version, content hash, and sync metadata in SQLite.
- Implement initial full sync and `since`-based incremental sync.
- Use transactions and atomic replacement so an interrupted sync preserves the last usable state.
- Provide synthetic contract fixtures for Zotero responses and schema variation.

**Exit criteria:**

- Repeating an unchanged sync performs no duplicate writes or downstream work.
- Adding, editing, moving, or deleting a fixture item produces the correct incremental state.
- Notes and annotations remain associated with the correct parent paper.
- Local database paths and private content are absent from logs and test snapshots.
- A real-library smoke test reports counts only and requires explicit user execution.

### V01-M2 — Interest Profile and Protected Export

**Goal:** Convert local library signals into a compact, explainable, privacy-bounded profile suitable for remote recommendation work.

**Implementation:**

- Define versioned `ItemDigest`, `InterestProfile`, and `RemoteProfile` schemas.
- Weight collections, manual tags, recent additions, abstracts, notes, highlights, and annotation comments as separate signals.
- Give user-authored annotation comments stronger weight than highlighted quoted text.
- Produce deterministic local keyword/topic candidates and capped extractive signals.
- Cache digests by normalized item content hash and prompt version.
- Aggregate long-term interests separately from recent focus.
- Infer core arXiv categories and one-hop adjacent category candidates with confidence and provenance.
- Include a bounded set of representative papers without raw notes or full abstracts.
- Apply a strict remote-field allowlist, per-field length caps, overall payload budget, and private-content scan.
- Export the profile atomically to a local protected file.
- Implement optional protected publication through GitHub CLI or API using stdin/encrypted transport, never command-line secret arguments.
- If DeepSeek assists profile aggregation, send only validated `ItemDigest` records and cache the result.

**Exit criteria:**

- Unchanged items do not regenerate digests or repeat LLM aggregation.
- The same normalized input and prompt/model version produce a stable schema-valid profile.
- The remote payload remains below the configured budget or fails with an actionable reduction report.
- A fixture containing secret-like strings, raw note HTML, and prompt-injection text cannot leak those values into the remote profile.
- The published profile can be consumed by a mock GitHub Actions job without appearing in logs.

### V01-M3 — arXiv Discovery and Retrieval

**Goal:** Reliably retrieve a bounded, recent, and sufficiently broad candidate set without scraping or violating arXiv limits.

**Implementation:**

- Add canonical arXiv ID and revision parsing.
- Build queries for categories and GMT submitted-date windows.
- Load a versioned adjacent-category map and cap expansion at one hop.
- Serialize all arXiv requests and enforce at least a three-second interval.
- Parse Atom responses into strict provider-neutral models.
- Add explicit timeouts, bounded retry/backoff, cache keys, and response metadata.
- Store the last successful checkpoint separately from in-progress run state.
- Query with a configurable overlap window and deduplicate across pages, categories, cross-lists, and revisions.
- Split large candidate requests by category/time while respecting the total ceiling.
- Preserve `published` for new-paper decisions and `updated` for revision tracking.
- Add already-seen and Zotero-library identifier indexes for later filtering.

**Exit criteria:**

- Contract tests cover valid feeds, empty feeds, malformed XML, timeouts, 429/5xx, pagination, cross-lists, and revisions.
- No test or production path can create parallel arXiv connections.
- A failed page does not advance the checkpoint.
- Re-running an overlapping window produces the same canonical candidate set without duplicates.
- The stored candidate record contains metadata and links only, never downloaded PDF content.

### V01-M4 — Recommendation and DeepSeek Pipeline

**Goal:** Produce a high-quality, explainable, diverse set of recommendations from the protected profile and arXiv candidates.

**Implementation:**

- Filter papers already in Zotero or recently recommended.
- Implement a transparent local pre-ranker using normalized title/abstract terms, topics, methods, categories, recency, representative papers, and feedback signals.
- Record score components for explanation and tuning.
- Define provider-neutral LLM request/response models and prompt versions.
- Implement the DeepSeek OpenAI-compatible adapter with `deepseek-v4-flash` as the default model.
- Batch LLM requests within candidate, token, timeout, retry, and cost budgets.
- Delimit all untrusted paper/profile content and validate structured JSON responses.
- Generate a configurable-language summary and concise recommendation reason.
- Apply a minimum quality threshold before quotas.
- Select core, adjacent, and exploration results with graceful quota reallocation.
- Apply diversity constraints for near-duplicate topics, papers, and author groups.
- Produce a versioned `RecommendationSet` and non-sensitive `RunManifest`.
- Cache model work by paper, profile version, prompt version, and model where semantically valid.

**Exit criteria:**

- A sanitized fixture run returns no more than 20 unique, schema-valid papers.
- Low-quality fixtures produce fewer than 20 rather than quota filler.
- Core/adjacent/exploration membership and score components are inspectable.
- Malformed or adversarial model output cannot control URLs, checkpoints, files, or selection outside validated fields.
- A partial LLM batch failure follows a defined policy and never publishes a partially validated result silently.
- Token usage, model requests, cache hits, duration, and estimated cost appear in the run manifest without private text.

### V01-M5 — Static Site, Encryption, and Browser Feedback

**Goal:** Deliver recommendations as a usable, privacy-aware static site without a runtime backend.

**Implementation:**

- Define a minimal publishable recommendation schema separate from internal ranking records.
- Build semantic, responsive static pages for today and historical dates.
- Display title, authors, categories, publication date, summary, recommendation reason, confidence, and arXiv abstract/PDF links.
- Add filters for date, topic, category, quota source, and feedback state.
- Add accessible loading, empty, error, outdated-data, keyboard, and focus states.
- Store pending feedback in a versioned `localStorage` schema.
- Support `interested`, `not_interested`, `save_for_later`, and `read` actions.
- Generate one batched, prefilled GitHub Issue URL for pending feedback and retain state until the user confirms submission.
- Implement a versioned authenticated encryption envelope using audited primitives compatible with Python and Web Crypto.
- Encrypt recommendation JSON in production mode; request the passphrase at runtime and never embed it in JavaScript.
- Keep an explicit public-output mode for users who accept public recommendations.
- Ensure useful paper links and a clear error remain available when JavaScript or decryption fails, without leaking protected content.

**Exit criteria:**

- The site works on current desktop and mobile browsers with no application server.
- Encrypted fixtures decrypt correctly with the right passphrase and fail safely with the wrong passphrase or modified ciphertext.
- Static artifacts contain no API keys, GitHub tokens, decryption passwords, raw profile, raw notes, or private matching evidence.
- Feedback survives reload, can be updated, and produces one bounded issue payload without a browser token.
- External text is escaped/sanitized and cannot execute script.
- Accessibility and static-build tests pass.

### V01-M6 — GitHub Automation and Feedback Loop

**Goal:** Run, publish, recover, and learn from feedback without manual daily execution.

**Implementation:**

- Add CI and production workflows with pinned reviewed Actions and least-privilege permissions.
- Schedule production at `10:17 Asia/Shanghai` and support `workflow_dispatch`.
- Add a production concurrency group to prevent overlapping publish/state updates.
- Load `DEEPSEEK_API_KEY`, protected profile data, and optional Pages passphrase through GitHub Secrets.
- Retrieve remote run state atomically from a dedicated state branch or approved equivalent store.
- Read, validate, deduplicate, and mark batched feedback Issues as processed.
- Convert feedback into short-term score boosts/penalties and long-term profile-review signals.
- Execute recommendation, encryption, static build, artifact inspection, and Pages deployment.
- Advance checkpoints and feedback state only after a successful validated publish.
- Preserve the previous site and state if any stage fails.
- Add run summaries and actionable failure diagnostics without private content.
- Document manual rerun, disabled schedule, stale profile, failed deployment, and state-recovery procedures.

**Exit criteria:**

- A manual workflow can deploy a complete sanitized end-to-end fixture site.
- Two concurrent triggers result in at most one production publisher.
- A forced failure at each stage preserves the prior checkpoint, feedback state, and usable site.
- A missed schedule is recovered by the next run's checkpoint window.
- The next recommendation fixture changes predictably after validated feedback ingestion.
- Workflow logs and artifacts pass automated secret/private-data inspection.

### V01-M7 — Release Hardening

**Goal:** Verify that the integrated system is safe, operable, documented, and ready for the first immutable release.

**Implementation:**

- Run the complete test matrix and schema/migration compatibility checks.
- Add end-to-end fault-injection scenarios for Zotero, arXiv, DeepSeek, state, encryption, and Pages failures.
- Measure first full sync, unchanged incremental sync, candidate ranking, model usage, site size, and complete scheduled run.
- Confirm configured ceilings for candidates, profile size, token usage, retries, and history retention.
- Review dependency licenses, lock file, third-party Actions, workflow permissions, and secret handling.
- Verify no real Zotero content exists in Git history, fixtures, logs, build artifacts, or release archives.
- Complete README setup/operation documentation and recovery guidance.
- Create `CHANGELOG.md` with the v0.1.0 user-visible summary.
- Run an explicit cost-bounded live smoke test using the real local environment and external APIs.
- Stabilize through `release/v0.1` only if integration fixes require a release branch.
- Create and publish immutable tag `v0.1.0` after all release criteria pass.

**Exit criteria:**

- All release acceptance criteria are evidenced and linked from the plan outcome.
- No critical or high-severity security/privacy issue remains open.
- Known non-critical limitations are documented with owners or target versions.
- Installation and recovery have been exercised from a clean environment.

## 10. Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| GitHub-hosted runners cannot reach local Zotero | Missing or stale profile | Separate local profile production from remote daily execution; publish only the compact profile |
| Profile exceeds GitHub Secret limits | Daily workflow cannot start | Enforce 30 KiB target, hierarchical compaction, representative-paper cap, and encrypted-blob fallback |
| Notes or annotations leak remotely | Privacy breach | Local-only raw storage, allowlist projection, redaction tests, artifact scans, no raw logging |
| Prompt injection in notes or arXiv text | Invalid or unsafe model behavior | Treat content as quoted data, strict schemas, URL allowlist, no model-controlled side effects |
| GitHub Pages content is publicly reachable | Research-interest disclosure | Authenticated client-side encryption enabled by default |
| Static feedback requires manual Issue confirmation | Lower feedback rate | Batch all daily feedback into one issue and keep local pending state until confirmed |
| GitHub schedule is delayed or dropped | Missing daily publication | Non-hour schedule, manual trigger, checkpoint catch-up, stale-result indicator |
| arXiv rate limits or transient failures | Incomplete candidates | Serialized throttling, bounded retry, cache, overlap, and checkpoint-on-success only |
| LLM cost or malformed output | Failed or expensive runs | Pre-rank locally, batch limits, token budget, cache, schema validation, preserve prior result |
| Interest profile overfits recent papers | Narrow recommendations | Separate long-term/recent interests and reserve adjacent/exploration quotas |
| Twenty results reduce quality | Poor trust | Apply quality threshold first and allow fewer results |
| Bot state commits conflict | Corrupt checkpoints/history | One concurrency group, atomic state update, dedicated state ownership |
| Initial architecture becomes over-fragmented | Slow development and duplication | Create modules only with real behavior; refactor by ownership, not file-count rules |

## 11. Privacy and Security Review Checklist

Before any real-data test or production deployment:

- Confirm raw Zotero fields allowed for local storage and fields allowed in each derived schema.
- Confirm note HTML sanitization and annotation parent ownership.
- Confirm profile projection uses a positive allowlist and overall size cap.
- Confirm model prompts contain only allowed derived Zotero data plus public arXiv metadata.
- Confirm prompts and responses are absent from default logs.
- Confirm browser assets contain no credentials or embedded passphrase.
- Confirm encrypted payload integrity failure is handled without partial rendering.
- Confirm Issue feedback destination and visibility are acceptable.
- Confirm workflows use least privilege and do not expose secrets to forks.
- Scan repository history, fixtures, caches, workflow artifacts, Pages output, and logs.
- Review third-party dependencies and Actions before pinning.

## 12. Persistence and Migration

Version v0.1.0 introduces schema version `1` for:

- Local Zotero state.
- Item digests.
- Interest and remote profiles.
- arXiv candidates and checkpoints.
- Feedback records and browser feedback storage.
- Recommendation sets and publishable recommendation data.
- Run manifests.
- Encrypted payload envelopes.

Requirements:

- Keep schema versions independent where their lifecycle differs.
- Store local SQLite migrations in ordered migration files.
- Make migrations transactional and test both new-database and upgrade paths.
- Write file migrations to a new artifact, validate it, and replace atomically.
- Never reinterpret an existing field silently.
- Record `prompt_version`, model, and profile version for cached LLM results.
- Provide a command or documented recovery path to rebuild derived state from the last safe source.

Because no application state exists before v0.1.0, the initial migration creates version-1 stores. Subsequent v0.1.x patches must remain backward-compatible or include an explicit tested migration.

### 13.2 Manual and Live Verification

Live checks are explicit and disabled by default:

- Zotero connection and count-only full/incremental sync.
- One bounded arXiv retrieval window.
- One bounded DeepSeek structured-output request.
- Protected profile publication to a test GitHub environment.
- Manual GitHub Actions run and test Pages deployment.
- Correct/wrong-passphrase browser checks.
- Batched feedback Issue submission and next-run ingestion.
- Full release-candidate run within the configured cost budget.

Live fixtures or responses containing private data must never be committed.

### 13.3 Release Quality Evidence

The final plan outcome must link or record:

- CI run and test summary.

- Security and artifact scan result.

## 14. Performance and Cost Budgets

Initial budgets are safety ceilings to be measured and refined, not quality targets:

- Process only changed Zotero items after the first full sync.
- Do not perform LLM work for an unchanged item digest/profile/model/prompt tuple.
- Retrieve no more than 1000 arXiv candidates per daily run by default.
- Pre-rank no more than 100 candidates and send no more than 80 to LLM ranking by default.
- Use bounded LLM batches and abort safely before exceeding the configured token/request budget.
- Keep the protected remote profile near 30 KiB and below its provider hard limit.
- Keep static history retention configurable; do not allow unbounded build growth.
- Reuse HTTP connections and stable cached provider results.
- Record full-sync, unchanged-sync, retrieval, ranking, build, and end-to-end durations.

Do not add a vector database, background queue, generalized distributed cache, or unbounded concurrency in v0.1.0.

## 16. Rollback and Recovery

- **Local sync:** wrap updates in transactions and retain the previous valid database/profile until replacement validation succeeds.
- **Profile publication:** retain the prior protected profile until the new payload passes schema, size, and privacy checks.
- **arXiv retrieval:** advance the checkpoint only after successful publication; rerun from the prior checkpoint plus overlap.
- **LLM failure:** publish nothing new and keep the previous site; do not silently substitute unvalidated prose.
- **Feedback:** mark Issue IDs processed only in the same successful state transaction as publication.
- **Pages:** deploy immutable artifacts and retain a documented path to redeploy the last known-good artifact or release.
- **Encryption:** retain envelope-version readers required to decrypt active history; migrate copies before removing an old reader.
- **Release:** tag only verified commits; hotfix from the released tag and merge the fix back to active development.

Destructive rebuild commands must require explicit target paths and preserve a backup or reproducible source.
