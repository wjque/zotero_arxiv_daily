# v0.1.1 Production Hardening and Recommendation Signals

- **Target version:** v0.1.1
- **Status:** Active

## 1. Objective

Harden the first production release without changing its local-first trust boundary or primary
workflow. v0.1.1 will make each published batch's time, profile version, and successful-deployment
identity inspectable; move scheduled model generation into the configured DeepSeek off-peak
window; add bounded, explainable preference signals for explicitly watched authors and
institutions; and correct operational issues discovered after the v0.1.0 release.

This is a backward-compatible patch release. Existing v0.1.0 profiles, encrypted Pages output,
feedback state, and arXiv state must remain readable throughout rollout.

## 2. Acceptance Criteria

v0.1.1 is acceptable only when all of the following are true:

1. The site displays the last successful recommendation generation start and completion times,
   the Zotero source-library version used by the batch, and a linkable successful deployment/run
   identity after decryption.
2. Stored timestamps remain timezone-aware UTC instants. User-facing timestamps and date filters
   render consistently in `Asia/Shanghai`, including dates that cross a UTC/local midnight.
3. The default scheduled run starts at `18:30 Asia/Shanghai` (`10:30 UTC`), inside the approved
   `18:30` through next-day `08:30` model-call window. Scheduled runs delayed outside the window do
   not incur model cost; a manual peak-time run requires an explicit override.
4. A stale site clearly identifies the age of the last successful batch without replacing a usable
   deployment with a failed or partial batch.
5. Users can configure bounded watched-author and watched-institution lists. Exact normalized
   author matches and explicit arXiv affiliation matches contribute separate inspectable local
   score components, while absent or ambiguous metadata contributes no bonus.
6. Preference bonuses are capped and cannot bypass model validation, minimum quality, quotas,
   deduplication, author diversity, URL validation, or publishable-schema validation.
7. The examples `Yann LeCun`, `Fei-Fei Li`, and `Saining Xie`, and aliases for DeepMind, Meta,
   OpenAI, ByteDance, CMU, MIT, and Stanford, can be represented by documented configuration. No
   person or institution is globally preferred unless the user configures it.
8. A canonical arXiv paper is not published again inside the configured suppression window after a
   successful deployment. Failed runs do not consume or advance recommendation history.
9. The production workflow uses reviewed, immutable Action revisions that do not produce the known
   Node.js 20 deprecation warning, retains least-privilege permissions, and passes artifact-safety
   inspection.
10. The static site has a coherent responsive visual hierarchy, automatic light/dark color
    support, accessible interaction states, and an English-only interface without adding remote
    fonts, scripts, trackers, or a client framework. The protected-data and feedback flows remain
    fully usable with keyboard and mobile input.
11. Formatting, lint, strict type checks, offline tests, package build, static-site build,
    compatibility tests, migration tests, and secret/private-content inspection pass. One explicit,
    cost-bounded production smoke run succeeds before tagging `v0.1.1`.

## 3. Scope

### 3.1 Included

- Versioned batch metadata for generation timing, profile identity, artifact build identity, and
  the last successful workflow deployment.
- `Asia/Shanghai` presentation and date-filter semantics at the site boundary.
- An off-peak schedule policy with a safe manual override and no-cost skip behavior.
- Configurable author and institution preference signals applied during local pre-ranking.
- Optional public arXiv affiliation parsing with strict size and field limits.
- Backward-compatible profile, arXiv-state, and publishable-site schema readers and migrations.
- Bounded recent-recommendation history and repeated-paper suppression.
- Stale-output indication and links to non-sensitive workflow diagnostics.
- Bounded static-site visual and usability refinement covering information hierarchy, typography,
  spacing, recommendation cards, status panels, badges, interaction states, responsive layout,
  automatic light/dark color schemes, and a consistent English interface.
- Current GitHub Action runtime upgrades, documentation corrections, and release hardening.

### 3.2 Non-goals

- Full-text PDF extraction, embeddings, a vector database, or semantic author disambiguation.
- Guessing an institution from email domains, paper text, author reputation, or model output.
- Querying a new scholarly metadata provider solely to fill missing affiliations.
- Guaranteeing discovery of every paper from a watched identity outside the categories and time
  windows already retrieved from arXiv.
- Allowing preference bonuses to override final model quality or diversity policy.
- Real-time deployment monitoring from the browser or embedding a GitHub token in Pages.
- Automatic local Zotero synchronization from GitHub Actions.
- Migrating to React, Vue, another client framework, a remote design system, remote fonts, or a CDN.
- Theme marketplaces, user-authored themes, animation-heavy interactions, dashboards, or a
  multi-page site redesign.
- Redesigning the feedback-learning model; that remains a v0.2.0 concern.

## 4. Current Baseline and Problems

### 4.1 Time and publication semantics

- The workflow currently starts at `02:17 UTC` (`10:17 Asia/Shanghai`), outside the requested
  off-peak generation window.
- `generated_at` is captured immediately before recommendation orchestration and therefore means
  generation start, although its name does not communicate that semantic.
- The publishable payload contains `generated_at`, but the browser does not display it.
- Paper `published_on` is produced by truncating an arXiv UTC timestamp to a date before local-time
  conversion, so date filters can be wrong near midnight in `Asia/Shanghai`.
- The static artifact is built before Pages deployment completes. It cannot honestly contain the
  future deployment completion timestamp. The served artifact itself proves that its batch
  deployed successfully; the workflow run identity supplies the auditable external status.

### 4.2 Profile and ranking semantics

- `RecommendationSet.profile_version` already carries the Zotero source-library version, but the
  publishable projection discards it.
- `RemoteProfile` has no explicit watched-author or watched-institution preferences.
- arXiv candidates preserve authors but currently discard optional public affiliation fields.
- Ranking exposes lexical, category, recency, and feedback components, but no identity preference
  components.

### 4.3 Repeated runs and operations

- A model-proposal cache prevents duplicate model work, but the production pipeline does not
  persist a bounded history of successfully published canonical IDs for short-term suppression.
- The previous usable Pages artifact survives a failed batch, but the page does not warn when its
  last successful data has become stale.
- The current site is intentionally minimal but does not provide sufficient visual hierarchy for
  the new batch status, profile version, deployment identity, recommendation metadata, and
  feedback controls. Its interface labels are also fixed English strings despite configurable
  recommendation output language.
- The README still describes v0.1.0 automation as incomplete, and pinned Actions currently produce
  a Node.js runtime deprecation warning.
- The completed v0.1.0 plan retains obsolete implementation follow-ups that should be reconciled
  without rewriting its historical outcome.

## 5. Architectural Approach

### 5.1 Canonical time model

All domain, persistence, manifest, and provider timestamps remain timezone-aware UTC instants.
`Asia/Shanghai` is the product presentation timezone, implemented through the standard-library
IANA zone database at the presentation and scheduling-policy boundaries. Naive local timestamps
must not enter schemas.

Replace the ambiguous v1 publication time with explicit v2 fields:

- `generation_started_at`: captured before ranking/model orchestration.
- `generation_completed_at`: captured after the complete recommendation set and manifest validate.
- `artifact_built_at`: captured when the atomic static artifact is finalized.
- `profile_library_version`: copied from the validated protected profile.
- `workflow_run`: an allowlisted run ID, attempt, source revision, and repository-relative run URL.

The UI renders these instants with `Intl.DateTimeFormat` using the explicit
`Asia/Shanghai` timezone and a stable localized format. It labels a served artifact as the last
successful deployment, displays its run identity, and calculates staleness from
`generation_completed_at`. It does not claim to know the completion time of a failed or currently
running deployment.

Schema-v1 input remains readable through a named compatibility adapter. For v1 data,
`generated_at` is labeled as an approximate generation-start time; no synthetic completion time is
invented. New output uses schema version 2 only after the compatibility tests pass.

### 5.2 Off-peak scheduling policy

The production cron changes to `30 10 * * *`, corresponding to `18:30 Asia/Shanghai`. Because
scheduled workflows may be delayed, a pre-model guard evaluates the actual local time using the
half-open policy window:

```text
[18:30, 24:00) or [00:00, 08:30]
```

A delayed scheduled invocation outside that window exits successfully before any DeepSeek call,
records a no-cost skip in the GitHub job summary, and does not change Pages or protected state.
`workflow_dispatch` receives an `allow_peak_generation` boolean input whose default is `false`.
A manual run outside the window must set it to `true`; arXiv-only diagnostics remain available
without the override.

Before production rollout, verify the applicable model's official off-peak pricing and congestion
policy. Provider pricing remains an operational assumption rather than a hard-coded scoring rule;
if the provider changes its window, update the cron, guard, operations documentation, and plan
decision note together.

### 5.3 Watched identity preferences

Introduce a bounded provider-neutral preference model owned by `profile/`:

- `watched_authors`: canonical display name plus optional aliases.
- `watched_institutions`: canonical display name plus optional aliases.
- Maximum entry, alias, and UTF-8 byte lengths enforced before profile publication.
- Default lists are empty for backward compatibility and to avoid globally imposed preferences.

The recommended configuration format is structured TOML/JSON arrays rather than a comma-separated
environment string. The protected `RemoteProfile` schema carries only normalized preference names
and aliases required by the remote local-ranking step. These fields remain inside the encrypted
profile Secret, are not copied into browser artifacts, and are not sent to DeepSeek.

Author comparison uses Unicode normalization, case folding, punctuation/whitespace normalization,
and exact normalized full-name or alias equality. It must not use substring matching. This reduces
false matches but cannot resolve homonyms without stable author identifiers; the limitation is
documented.

Institution comparison uses only non-empty affiliation strings explicitly supplied by the arXiv
Atom response. Aliases support forms such as `Google DeepMind`/`DeepMind`, `Meta AI`/`FAIR`,
`Carnegie Mellon University`/`CMU`, and `Massachusetts Institute of Technology`/`MIT`. Missing
affiliation is treated as unknown, not as a negative match. External text and alias values are
validated and bounded at their adapters.

Pre-ranking adds two inspectable score components:

- `watched_author`: one fixed bonus if any configured author matches.
- `watched_institution`: one fixed bonus if any configured affiliation matches.

Multiple matches do not accumulate without bound. The combined identity bonus is capped below the
sum needed to override the existing category, quality, and diversity gates. Exact weights and the
cap must be fixed by deterministic ranking tests before implementation completion and documented
as configuration defaults, not hidden constants.

### 5.4 Recommendation history

Add a versioned, bounded public-metadata history store containing only canonical arXiv IDs,
revision numbers, and successful publication timestamps. The default suppression window is 14
days, and retention is capped at 30 days. History is prepared during generation but copied to the
protected `state` branch only after Pages deployment succeeds, preserving checkpoint-on-success
semantics.

The suppression decision is local and precedes model calls. A repeated run with unchanged inputs
must not spend tokens on suppressed candidates. Empty eligible input produces a valid empty batch
and manifest without calling DeepSeek.

### 5.5 Deployment observability

Extend the non-sensitive run manifest and site payload through explicit allowlists. The protected
site may display:

- Last successful generation interval in `Asia/Shanghai`.
- Zotero source-library version and profile schema version.
- Successful workflow run ID/attempt and source revision.
- Recommendation count and stale/fresh state.

It must not expose Secrets, raw profile terms, watched identity lists, prompts, response bodies,
Zotero content, local paths, or protected state. Workflow summaries may contain counts, durations,
safe failure categories, and the local scheduling decision only.

### 5.6 Static-site visual and usability refinement

Keep the existing self-contained HTML, CSS, and browser JavaScript architecture. Reorganize the
page around a compact header, a last-successful-batch status panel, filter controls, recommendation
cards, and the explicit feedback export panel. Establish reusable CSS custom properties and
component classes within the site owner rather than introducing a general design-system package.

The visual slice includes:

- A readable type scale, spacing scale, content width, and clear primary/secondary metadata.
- Status treatments for fresh, stale, loading, empty, decryption failure, and safe fallback states.
- Consistent badges for category, quota source, confidence, and locally matched preference signals
  without exposing the configured watchlists.
- Distinct summary, recommendation-reason, paper-link, and feedback-action regions.
- Mobile layouts that do not require horizontal scrolling at a 320 CSS-pixel viewport.
- Automatic `prefers-color-scheme` light/dark palettes with WCAG AA text and control contrast.
- Visible keyboard focus, semantic landmarks and headings, minimum touch targets, and
  `prefers-reduced-motion` behavior if any transition is retained.
- An English-only interface catalog, including human-readable feedback-action labels, independent
  of the configurable language used for generated recommendation prose.

Do not load remote fonts, icons, images, CSS, scripts, analytics, or trackers. Prefer system fonts,
CSS decoration, and repository-owned SVG only when a visual cannot be expressed accessibly in
HTML/CSS. External recommendation text remains text-node-only. Set and test explicit compressed and
uncompressed size budgets for the generated HTML, CSS, and JavaScript before completing the
milestone; a visual change that exceeds them requires a recorded justification.

## 9. Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| DeepSeek changes pricing hours | Unexpected model cost | Verify before release; runtime window guard; manual override defaults off; document operational assumption |
| GitHub scheduled-run delay | Model call occurs outside approved window | Evaluate actual `Asia/Shanghai` time immediately before the first model request and skip safely |
| Affiliation data is sparse or inconsistent | Institution bonus is often absent | Treat affiliation as optional; support aliases; never infer; document coverage limitation |
| Author homonyms or name variants | False positive/negative bonus | Exact normalized aliases only; no substring/fuzzy matching; cap bonus; document lack of stable IDs |
| Identity bonus dominates relevance | Lower-quality recommendations | Separate capped components; retain quality, category, quota, diversity, and model-validation gates |
| Schema rollout breaks the current Secret/site/state | Production outage | Read v1 and v2; write v2 only after compatibility tests; keep last known-good Pages artifact |
| Misleading deployment status | Page claims success without evidence | Describe the served batch as last successful; expose run identity; never fabricate completion time |
| Local date conversion changes filtering | Papers appear under a different calendar date | Preserve UTC instant, derive local date consistently, and test UTC-midnight boundaries |
| History state push fails after deployment | A later run may repeat papers | Keep the failure visible; use idempotent history records; reconcile from the last successful manifest during recovery |
| Public metadata leaks user preferences | Privacy loss | Keep watchlists in the protected profile only; publish match outcome at most, never the lists |
| Visual changes reduce accessibility or inflate artifacts | Site becomes harder or slower to use | WCAG AA contrast, keyboard/mobile checks, reduced-motion support, no remote assets, and explicit HTML/CSS/JS size budgets |

## 10. Privacy and Security

- Raw Zotero records, notes, annotations, PDF text, and local digest evidence remain local.
- Watchlists are user preference data. They cross only the already approved protected-profile
  boundary, remain in the GitHub Secret/runtime, and never enter Pages or provider prompts.
- arXiv author and affiliation strings are untrusted public input: normalize after strict parsing,
  enforce bounds, and render only through text nodes.
- LLM output cannot assert or create an author/institution match and cannot change identity weights,
  timestamps, deployment state, history, URLs, or checkpoints.
- Run URLs and revisions must be derived from validated GitHub environment fields and repository
  identity; arbitrary URLs are rejected.
- Artifact inspection must scan plaintext and encrypted build metadata for credentials, watched
  lists, raw profile fields, prompts, response bodies, and local filesystem paths.

No new trust-boundary ADR is required if implementation follows these constraints. Introduce an ADR
before adding a third-party affiliation service, publishing watchlists, or changing encryption/state
ownership.

## 11. Compatibility and Migration

- **Application version:** bump the single authoritative version to `0.1.1` only during release
  hardening.
- **Remote profile:** read schema v1 as empty watchlists; write schema v2 after local rebuild. Profile
  activation is explicit through `profile publish-github`.
- **arXiv state:** migrate schema v1 atomically by adding optional affiliations or retain a named v1
  adapter if the candidate schema is separated from checkpoint state. Preserve the previous file
  until validation succeeds.
- **Publishable site data:** read v1 and v2; generate v2 for new builds. Existing encrypted v1 Pages
  artifacts remain decryptable and display a limited legacy timestamp label.
- **Feedback:** browser and Issue feedback schemas remain unchanged.
- **Recommendation history:** introduce schema v1 with an empty-state migration and bounded
  retention. It contains public arXiv identifiers only.
- **Configuration:** existing configuration remains valid. New preference lists default to empty;
  the scheduling timezone defaults to `Asia/Shanghai`.

Migration must be explicit, atomic where persisted files change, and covered by fixtures for the
exact v0.1.0 formats.

## 12. Test and Verification Strategy

### 12.1 Unit tests

- UTC-to-`Asia/Shanghai` conversion before, at, and after midnight.
- Off-peak membership at `18:29`, `18:30`, `23:59`, `00:00`, `08:30`, and `08:31`.
- Injected clocks for generation start/completion and stale-age calculations.
- Unicode/case/punctuation/whitespace normalization for author and institution aliases.
- Exact-match, alias-match, missing-affiliation, homonym, substring-rejection, and bonus-cap behavior.
- Identity bonuses preserve minimum quality, quota, and author-diversity constraints.
- Empty and fully suppressed candidate sets do not call the provider.
- Static-site interface assets contain English labels only, including readable feedback actions,
  while the generated-prose language remains a configurable presentation setting.
- Feedback adjustments reach both shortlist construction and final local selection.
- Candidate revision/content changes invalidate cached model proposals; malformed or empty
  structured model output is retried only within the bounded request budget.

### 12.2 Contract and migration tests

- v0.1.0 profile v1 to v2 defaults and strict unknown-field rejection.
- Atom feeds with no affiliation, one affiliation, multiple authors, malformed fields, and oversized
  fields.
- arXiv state v1 migration and rollback after invalid replacement.
- Publishable v1 compatibility and strict v2 metadata/run URL validation.
- History empty/repeated/expired/revision/retention behavior.
- Encrypted schema-v2 round trip and wrong-passphrase/tamper behavior.

### 12.3 Integration and end-to-end tests

- Scheduled run inside the window completes and records a successful batch.
- Delayed scheduled run outside the window performs no DeepSeek request and changes no state.
- Manual peak run fails closed without override and proceeds with an explicit override.
- Failed retrieval, model, site build, Pages deployment, or state push preserves the prior usable
  site and appropriate prior checkpoints.
- Successful deployment advances recommendation history; a repeated run suppresses prior papers
  before provider work.
- Static site displays local times, profile version, run identity, stale state, and correct local
  date filtering using synthetic data only.
- Static site remains usable at 320 CSS pixels, with keyboard-only input, light and dark color
  schemes, reduced-motion preference, long synthetic titles/authors, empty results, and all safe
  error states.
- Generated HTML, CSS, and JavaScript contain no remote runtime dependency and remain within the
  approved per-asset and total size budgets.

### 12.4 Release gates

Run:

```bash
uv run ruff format --check .
uv run ruff check .
uv run mypy
uv run pytest
uv build

```

Inspect the generated site and state fixtures for secrets, watched identities, raw Zotero content,

production smoke run and confirm Pages, run metadata, profile version, history persistence, and
subsequent repeat suppression.

## 13. Rollback and Recovery

- Keep v1 readers until no deployed or protected active artifact requires them.
- Generate migrated state beside the old file, validate it, and replace atomically; retain the old
  file for recovery until the run succeeds.
- If identity ranking degrades quality, clear the configured watchlists or set bonuses to zero; no
  stored Zotero data changes are required.
- If the new cron or pricing assumption is wrong, disable the schedule or restore the last verified
  off-peak cron without changing application data.
- If a new batch fails, do not deploy it and do not advance arXiv, feedback, proposal, or
  recommendation-history state.
- Redeploy the last known-good Pages artifact/release if site schema-v2 rendering fails.
- Do not move the `v0.1.0` tag. Any post-release correction is a new patch version.
