## Objective

Replace the opaque Zotero library revision shown on the site with a timestamped profile snapshot
that has direct user meaning, reduce the visual prominence and density of batch-status metadata,
and present each generated batch in a deterministic relevance order.

## Acceptance Criteria

- New remote profiles retain an aware UTC source-library synchronization instant.
- New publishable data displays that instant as `Profile snapshot` in `Asia/Shanghai`; it never
  exposes the opaque Zotero revision number.
- Existing remote-profile v1/v2 and publishable-site v1/v2 data remain readable and omit unavailable
  snapshot information safely.
- Batch status uses compact typography, spacing, borders, and metadata layout while retaining all
  applicable generation, artifact, and workflow information.
- Final recommendation cards are ordered by local preference relevance, then validated model quality,
  then latest arXiv revision time and canonical arXiv ID; diversity quotas remain selection-only
  constraints and are not presented as grouped sections.
- Full formatting, lint, strict typing, offline tests, package build, static-site build, and artifact
  inspection pass before deployment.

## Scope and Non-goals

Scope includes local synchronization metadata, remote-profile v3, publishable-site v3, adapters,
final recommendation ordering, static-site rendering, tests, and documentation. It does not change
candidate selection quotas, model prompts, raw Zotero sharing, browser secrets, historical
recommendation data, or the scheduled workflow policy.

## Architecture and Migration

`ZoteroStore` records the successful local synchronization instant beside its internal revision.
Remote-profile v3 projects that non-sensitive timestamp, and publishable-site v3 carries it to the
browser. v1/v2 readers adapt missing timestamps to `None`; the UI omits the field rather than
inventing a time. Existing opaque revisions remain internal synchronization state only. After the
existing quota and diversity selector has chosen its set, final records sort by local score,
validated LLM quality, candidate update time, and canonical ID. The model cannot add papers or
override local selection policy.

## Risks, Privacy, and Recovery

The timestamp reveals only when a profile source last synchronized, not Zotero items, notes,
annotations, identifiers, or profile content. If legacy profiles are not rebuilt, the site omits the
snapshot. Rollback is a code revert; old profile and publishable readers remain supported.

## Verification Strategy

Test timestamp creation and validation, legacy profile/publishable migrations, profile-to-site
projection, final ordering ties and priority, compact asset content and size budgets, malformed
timestamps, and encrypted/public site builds. Run the full offline gate and inspect generated
artifacts before an approved production deployment.

## Decision Notes

### 2026-08-02 — Snapshot meaning

- Selected the successful local Zotero synchronization instant as the user-facing profile snapshot.
  It identifies when the source library state was captured without misrepresenting the opaque API
  revision as a count or application version.

### 2026-08-02 — Local API tombstone fallback

- The configured Zotero Local API returned HTTP 404 for its incremental deleted-record endpoint
  while items and collections remained available. Instead of silently retaining deleted records,
  the adapter fetches a complete snapshot and atomically reconciles missing items and collections.

### 2026-08-02 — Production verification

- A complete local snapshot synchronization retained 732 current records and deleted none. The
  rebuilt protected remote profile was schema v3 and included a profile snapshot before publication.
- Approved-window production run `30749797954` on `fb8f612ff546000e0743984e83c23af10a891ed6`
  retrieved 998 candidates, generated 20 recommendations with two model requests, passed artifact
  inspection, deployed Pages, and persisted protected state successfully.

### 2026-08-02 — Final card ordering

- The final page order is deliberately separate from candidate selection: local relevance is the
  primary signal, validated model quality is secondary, and update time plus canonical arXiv ID
  provide deterministic ties. Existing source quotas and diversity constraints choose the batch but
  do not make the reading order look like quota groups.
- Production run `30750247331` on `8ed8627eda60c113dd560384f84c9f3c8fd842a9` verified the
  ordering code through the scheduled pipeline: 998 candidates produced 20 encrypted
  recommendations with one model request; artifact inspection, Pages deployment, and protected
  state persistence all succeeded.
