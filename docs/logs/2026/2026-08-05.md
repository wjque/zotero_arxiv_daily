# 2026-08-05

## Summary

- Hardened the active v0.2.0 release candidate in response to the zero-overlap evaluation result,
  unauditable LLM efficiency measurements, and public plaintext workflow-state exposure. The
  immutable v0.2.0 plan was not changed.

## Added

- Added AES-GCM encrypted workflow-state bundles with validated required/optional file allowlists,
  atomic owner-only local writes, `state encrypt` / `state decrypt` commands, and a dedicated
  `ZAD_STATE_ENCRYPTION_KEY` configuration value distinct from the Pages passphrase.
- Added one-time legacy state migration and a manual-only, lease-protected encrypted-root history
  purge action. ADR-0001 defines the key, migration, rollback, and exposed-history requirements.
- Added candidate-positive and candidate-negative coverage plus candidate-conditional Recall to
  ranking metrics. Shadow comparison and the coarse Recall@60 gate now treat zero candidate-label
  overlap as unavailable rather than ranking quality evidence.
- Added provider-neutral completion usage, measured token/latency/cost manifest fields, privacy-safe
  manifest history, and `evaluate efficiency` median comparison. The comparison fails closed when
  actual token usage is missing or the 25% output-token target is not met.
- Added a bounded categorical preference-context allowlist and ADR-0002. Only up to four approved
  signal names can reach `explain-v1`; `judge-v1` remains limited to public candidate metadata.

## Changed

- The production workflow writes only `state.enc.json` to the `state` branch and restores state only
  after authenticated decryption and schema validation. Missing state branches may initialize empty;
  invalid, missing, or undecryptable persisted state fails closed.
- Manual refinement canaries retain a separate preference-context approval input. Scheduled runs keep
  refinement and preference context disabled, and manifests record whether the context was enabled.
- README and v0.2.0 release notes now describe conditional Recall interpretation, measured efficiency
  comparison, encrypted state operation, and the explicit history-purge precondition.

## Later Update

- Switched the production workflow and `.env.example` to the quality-first `judge-v2`/`explain-v2`
  path. The frozen v0.1.2 proposal prompt remains unchanged; proposal validation now rejects
  obviously short or generic reasons. Judge prompts use fixed evidence anchors and uncertainty,
  explanation prompts require problem/approach/result/relevance/limitation grounding, and both
  refinement outputs require at least two exact evidence fields. Quality scores now apply the
  judge uncertainty as a confidence discount, and old v1 refinement cache entries are ignored.
- Added a `proposal-v2` factual-grounding prompt for the explicit non-refinement fallback while
  preserving the frozen v0.1.2 proposal prompt and hash used by baseline replay. Its cache namespace
  is versioned separately so old low-quality proposal text is not reused.
- Classified refinement JSON-envelope failures separately from invalid cached entries and reduced the
  default judge/explanation batch sizes to 20/10 with an eight-request bound. This intentionally
  spends more model calls to improve structured-output adherence and prose quality.
- Normalized exact arXiv identities from Zotero URLs, `arXiv:` markers, and arXiv DOIs. Added
  `evaluate hydrate-candidates`, which fetches exact public IDs from an immutable snapshot into an
  evaluation-only candidate state; production retrieval never consumes that state. ADR-0003 records
  this boundary and the no-fuzzy-match rule.
- Hydrated 31 exact public candidates for snapshot `eval-2ba068b1dc6c9b13320467b6` in two requests;
  one non-arXiv DOI remains explicitly unresolved. The temporal holdout now has 7
  candidate-overlapping labels and candidate Recall@60 `1.0` for both baseline and candidate; the
  previous zero-overlap `Recall@60=0.0` is no longer used as ranking evidence. The current candidate
  remains blocked on quality evidence: NDCG delta `+0.015` is below `+0.05`, and negative-label
  rate increased.
- LLM efficiency remains recorded as an observation only. A higher token count or unavailable
  provider cost does not block the quality-first canary.
- The successful quality canary `30973426366` ran 40 candidates through 5 model requests, selected
  20 recommendations, deployed Pages, and persisted encrypted state tip `752a98b`. It recorded
  26,817 input tokens and 8,273 output tokens with preference context disabled; no efficiency
  comparison was requested. Workflow summaries now suppress stale efficiency reports unless the
  explicit comparison input is enabled.
