# 2026-08-04

## Summary

- Continued the active v0.2.0 personalized-ranking plan without changing production activation,
  publishing runtime data, or adding a new approved trust boundary.

## Added

- Added applicability-aware normalized ranking feature groups, immutable local weight-set registry
  definitions, reversible active pointers, score contributions, and source-aware exploration reserve.
- Added a local `evaluate snapshot` / `evaluate shadow` workflow. It freezes corpus inputs, compares
  the frozen v0.1.2 scorer with the active local weight set, reports aggregate Recall/Precision/NDCG,
  negative-label rate, calibration/diversity/coverage metrics, and feature-group ablations, and writes
  owner-only ignored reports without changing runtime recommendation state.
- Added a gated two-stage LLM recommendation path. `judge-v1` supplies bounded quality and uncertainty
  features to local selection; `explain-v1` produces summary/reason/limitation text only for final
  selections. Judge and explanation caches remain separate and validated before they are written.
- Added publishable-site schema v4 with an optional limitation note and retained exact v1-v3 readers.
- Added lockfile-backed Playwright browser tests for desktop and mobile Chromium. They decrypt a
  backend-generated AES-GCM schema-v4 fixture, render quality/uncertainty/limitation fields, and
  confirm unsupported schemas fail closed; CI now runs this gate.

## Changed

- Corrected normalized coarse ranking to classify core, adjacent, and exploration candidates correctly.
  Missing or inapplicable evidence is excluded from score normalization rather than interpreted as zero.
- The daily workflow persists the local ranking weight registry after a successful deployment. LLM
  refinement and its categorical preference context remain disabled by default; the latter needs a
  field-level trust-boundary approval before it can be enabled.
- Updated the v0.2.0 plan after the arXiv outage and release-readiness review. Corpus size now controls
  uncertainty reporting rather than a fixed release gate, while automatic tuning remains disabled;
  the evolving corpus is evaluated through immutable pinned snapshots.
- Required LLM judging and explanation to receive complete normalized titles and abstracts, with
  deterministic whole-record batching, bounded retries/cost, and explicit oversized-record handling
  replacing character truncation.
- Expanded V020-M8 release hardening to cover browser schema v4 execution, arXiv retry spacing and
  validated-pool degradation, strict state restoration, deploy/state reconciliation, explicit ranker
  rollback, and confirmed ranking/cache/metric correctness defects.
- Added two-phase workflow state reconciliation. A prepared deployment persists the generated batch,
  candidate state, caches, and history candidate before Pages deployment; a later run checks the prior
  Deploy step and records impressions/history exactly once when the state push was interrupted.
- Exposed bounded LLM batch, request, retry, byte, and output-token settings through `AppConfig` and
  `.env.example`; DeepSeek response bodies now have a 2 MiB adapter limit. Sparse evaluation warnings
  remain separate from the automatic-tuning eligibility flag, while explicit activation remains a
  manual action.
- Corrected symmetric hyphen/space facet matching and retained bounded arXiv degraded diagnostics
  without copying provider response bodies into local state.
- Propagated candidate-pool degradation and its source checkpoint into the private run manifest and
  static-site freshness metadata; the browser batch status now labels a recent validated fallback.
- Bumped the authoritative application version to `0.2.0`, documented the local release candidate in
  README and CHANGELOG, and marked completed browser, deployment-reconciliation, and normalized-ranker
  plan items accurately while retaining production evidence milestones as Active.
- Updated the repository engineering standard so newly written plans are immutable unless the user
  explicitly authorizes a specific edit. Future plans contain only stage goals, milestone behavior,
  and measurable acceptance methods; implementation design, progress, and outcomes belong in code,
  tests, ADRs, logs, changelogs, or release records.
- Required agents to reassess implementation choices throughout development and debugging, prefer a
  coherent refactor over patch-on-patch changes when it materially improves efficiency or simplicity,
  remove superseded paths, and support performance claims with measurements.

## Compatibility and Migration

- Publishable schema v4 carries an optional bounded limitation. v1-v3 payload readers default it to
  unavailable. The local weight registry is newly created ignored owner-only state and defaults to
  `coarse-v1`; it has no impact on existing deployments until a new run persists it.
- The application package now identifies as `0.2.0`; all v0.1.x persisted profile, feedback,
  candidate, recommendation, and publishable inputs retain explicit compatibility paths.
